# Human-in-the-loop — обязательное утверждение результатов и действий агентов
Дата решения: 2026-11-22. Утверждено пользователем. Данный документ — проектная спецификация, не действующая функция.

## Главный принцип
Каждый агент создаёт собственный анализ и рекомендации, с указанием источников, неопределённостей, версии данных и предлагаемых действий. Только уполномоченный пользователь принимает окончательное решение: передать в работу, отклонить, вернуть на доработку, сохранить без дальнейших действий, запросить дополнительную информацию. Нельзя считать рекомендацию ИИ разрешением на исполнение.

## Линия ответственности
- Агент-источник: подготавливает анализ и рекомендации, не меняет оригиналы документов и не отправляет результаты сторонним лицам без отдельного разрешения.
- Координатор: фиксирует ожидающее решение, проверяет адресата и права; не принимает финальное решение вместо пользователя.
- Уполномоченный пользователь: выбирает решение применительно к конкретной версии заключения и разрешённым операциям, по компании и в пределах своей роли.
- Агент-исполнитель: получает только согласованный набор данных и формальное поручение; подготавливает проект результата. Дополнительные внешние действия (отправка претензии, публикация, платёж, изменение документов, запуск production, сдача отчётности) требуют самостоятельного разрешения.

## Статусы
analysis_in_progress -> recommendation_ready -> awaiting_approval ->
approved_for_handoff / rejected / revision_requested / archived_without_action.
После approved_for_handoff создаётся отдельный execution_task с независимыми статусами и отдельными правами. Подготовка результата НЕ равна исполнению внешнего действия.
Не путать 'saved/archived' и 'approved'.

## Карточка решения
decision_id UUID; organization_id/tenant_id; originating_agent; analysis_id/version/hash; source_document_ids/version_ids; summary; risks; assumptions; recommended_actions; suggested_recipient; proposed_scope; created_at; expires_at; reviewer_user_id; reviewer_role; decision(status); signed/verified decision proof; decision_at; comments; delegated_task_id; idempotency_key; audit_event_ids.
При изменении анализа или документов подтверждение старой версии становится недействительным. Выводы и допущения показывать до кнопок.

## Управление доступом
Проверять on-server MAX user_id, tenant, role, grants и конкретное право approve/assign. Для финансовых и юридически значимых операций нельзя полагаться на callback payload как единственное доказательство; callback привязывается к серверной одноразовой операции с TTL, nonce, replay-protection и последующим подтверждением в зависимости от класса риска.
По умолчанию запрещать межагентное изменение или передачу документов; передавать по ссылкам на разрешённые и проверенные очищенные копии, не оригиналы.
Кнопки: «Передать в работу», «Вернуть на доработку», «Отклонить», «Сохранить без передачи», «Запросить уточнение». Все действия журналируются и доступны для аудита.

## Пример
Бухгалтер -> подтверждает задолженность по ОСВ и договорам -> предлагает передать досье юристу -> директор утверждает именно передачу -> юрист готовит заключение и проект претензии -> директор отдельно решает, отправлять ли претензию -> после подтверждённого поступления навигатор фиксирует фактический эффект. Учетные данные и внешние отправки не изменять автоматически.

## Приёмочные тесты
Неавторизованный пользователь, бухгалтер без права approve, чужая организация, устаревшая версия анализа, повторный callback, истёкший срок, частично подтверждённое решение, отмена делегирования, запрещённая публикация или отправка без второго подтверждения, отказ целевого агента, отмена решения до фактического исполнения, сохранение полного аудита.
Применять правило ко ВСЕМ агентам (юрист, бухгалтер, менеджер, маркетолог, разработчик, преподаватель), а не только FinExpert.
