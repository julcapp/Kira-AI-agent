# Межагентная связь «Бухгалтер → Юрист → Персональный финансовый навигатор»
Дата: 2026-11-22. Статус: согласованная архитектурная концепция; код и интеграция не реализованы.
Публичный сервис «Ваш Финэксперт», внутренний координатор платформы «Кирюша». Юридический агент разрабатывается отдельным направлением. ОДДС добавлен в бухгалтерский контур.

## Разграничение ОДДС / УДДС / платёжного календаря
- **ОДДС** — отчёт о движении денежных средств как компонент бухгалтерской (финансовой) отчётности организации, при наличии и применимости; сравнивается с опубликованными годовыми формами/регистрами. Отдельный от ОСВ и ОФР документ. Не всегда обязателен для каждого субъекта в одинаковом объёме.
- **УДДС** — внутренний управленческий отчёт по реальным поступлениям/платежам, направлениям деятельности и статьям ДДС, требует дополнительных внутренних данных (банк/касса/операции/ERP), не может корректно выводиться только из внешней годовой БФО.
- **Платёжный календарь** — план будущих поступлений/платежей, сроки, сценарные кассовые разрывы; прогноз, не факт.
В бухгалтерском мастере запросов 1С добавить ОДДС в набор по задачам, если он применим и доступен; для финансовой оценки после завершения периода. Управленческие формы подключить на втором этапе.

## Первый межагентный сценарий: взыскание дебиторской задолженности
1. Бухгалтер анализирует ОСВ, карточки счетов 62/76 и подтверждающие договоры/акты; показывает сумму, контрагента, сроки, дату сверки, основания и ограничения. Сам факт положительного сальдо без условий договора не доказывает просрочку.
2. По условиям договора и подтверждённым документам создаёт предложение «Направить на юридическую проверку». Подтверждение уполномоченного директора/представителя обязательно.
3. Coordinator создаёт case с UUID и человекочитаемым CASE-YYYY-NNNNNN (не глобальный секрет), tenant/org, originating_agent='accountant', receiving_agent='lawyer', debtor_ref, debt_amount+currency, evaluated_at, urgency, purpose, required_deliverable, due_date_if_approved, created_by, approved_by, status и policy_version.
4. Case содержит **references** на разрешённые immutable redacted/sanitized документные версии и provenance (исходный file UUID, проверка SHA-256, лист/строка/пункт договора); оригиналы и token mapping не передаются внешним моделям. Если юридическому анализу нужны реальные реквизиты, это отдельная авторизованная локальная операция внутри инфраструктуры — не обход redaction policy.
5. ИИ-юрист после проверки правового основания и полноты доказательств возвращает статус: 'needs_documents' / 'legal_review' / 'draft_ready' / 'blocked' / 'completed', проекты претензий и рекомендации; проверяет применимые сроки, порядок взыскания и доказательства, не обещает успешного взыскания. Направление претензии, иска, исполнительных документов — только после отдельного согласования человеком и соблюдения специальных юридических требований.
6. Бухгалтер получает юридический результат, но не может автоматически менять проводки либо признавать поступления. Финансовый навигатор отображает stage, финансовый прогноз возможного погашения при явных сценарных допущениях и затем фактические поступления из учётных данных.
7. После закрытия case: журнал управленческих решений с ожидаемым и фактическим эффектом, обратной связью и первоисточниками. Закрытие дела не равно поступлению денег.

## Минимальный API/event contract (проект)
- POST /cases/debt-review (authenticated director-approved): {organization_id, debtor_ref, source_analysis_id, amount, currency, document_version_ids[], request_goal}
- events: debt_case.created, debt_case.approved, debt_case.accepted, debt_case.needs_documents, debt_case.legal_opinion_ready, debt_case.closed, debt_case.actual_payment_matched
- payload: event_id, trace_id, case_id, tenant_id, org_id, actor, agent_from, agent_to, evidence_refs[], timestamp, schema_version, redaction_policy_version
- Только ID/reference и допустимые минимум-поля в событиях, без ФИО/ИНН/банковских реквизитов в queue/logs.
- Идемпотентность event_id, outbox/inbox, журнал переходов, права на события. Передача case между агентами не означает общее право читать все документы.
- Обязательны origin, receiving agent, task goal, status, result references, granted permissions и accountability.

## Контрольные кейсы
- Дебиторская задолженность ещё не просрочена — юридическая задача не называется просроченной автоматически.
- Нет договора/акта/подтверждённой суммы — статус needs_documents, не автоматическое формирование претензии.
- Бухгалтер обслуживает несколько компаний — запрет перекрёстных ссылок/контрагентов/документов.
- Документ A01 и B01 нельзя путать с оригиналом; сохранять точную родительскую версию.
- Руководитель отменил делегирование — остановить новый доступ к файлам и передачу задач.
- Юрист запрашивает необезличенные реквизиты — только локальное разрешённое раскрытие нужных полей.
- Дата/сумма оплаты обновлена — не считать полное взыскание без подтверждения банковским/кассовым фактом.
- При недоступности юридического агента кейс остаётся в очереди со статусом ожидания, не теряется.

## Внедрение
Сначала реализовать независимые схемы кейса и событий, проверку tenant/grant и документных версий, затем synthetic интеграционные тесты. Обсуждение юридического агента ведётся отдельно, здесь фиксируется только межагентный контракт. В production не внедрять до проверки и одобрения.
