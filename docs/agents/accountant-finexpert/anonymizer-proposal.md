# Ваш Финэксперт — модуль «Анонимайзер»: обсуждаемая концепция
Дата 2026-11-22. НЕ утверждён к разработке в полном объёме. Production не изменён.
## Задача
Рассмотреть маскирование и псевдонимизацию документов, загруженных через кабинет пользователя, прежде чем данные передаются для AI-анализа, в том числе специализированному аналитическому инструменту Codex. Закрытый tenant-контур НЕ означает, что нет передачи внешнему AI-провайдеру.
## Обсуждаемые уровни
1. Защищённый внутриорганизационный анализ оригиналов, RBAC/ABAC, аудит и шифрование; не называть его обезличиванием.
2. Псевдонимизация: имена/названия сторон/ИНН/банковские счета/контакты заменяются стабильными токенами; ключ отображения хранится в отдельном защищённом хранилище; не обещать полной анонимности.
3. Обработка с усиленным исключением коммерчески чувствительных полей, понижение детализации или локальный расчёт. Риск потери аналитической полезности.
## Что сохранять для бухгалтерского анализа
Бухгалтерские номера счетов 60, 62, 68, 90 и др., суммы, период, дебет/кредит и последовательность операций — при необходимости и с обоснованием. Банковские расчётные счета, личные ФИО, ИНН физлиц, контакты — маскировать/заменять, если задача не требует исходников. Реквизиты ЮЛ тоже могут быть коммерчески чувствительными. Суммы и даты могут служить квази-идентификаторами: оценивать риск обратной идентификации.
Внешняя ИИ-модель получает только подготовленный минимальный набор, а не исходный документ; при локальном анализе может быть разрешена работа с оригиналом при наличии полномочий.
## Архитектура (проект)
original (encrypted tenant storage) -> sensitive-field detection -> policy per task/provider -> deterministic redaction/pseudonymization -> preview user -> validated AI input -> audited result -> mapping back on tenant side (only for authorized role).
Операции с токенизацией должны быть детерминированными в пределах tenant, версии проекта и периода, с ротацией и запретом межарендной корреляции. Удалять скрываемые данные из внутренних XML/PDF слоёв, метаданных, формул и скрытых листов, а не только закрашивать визуально. Проводить тесты восстановления текста из PDF и исходных таблиц.
## Регулирование
Закон №152-ФЗ и приказ Роскомнадзора №140 от 19.06.2025 о требованиях и методах обезличивания (в силе с 01.09.2025) требуют юридического рассмотрения конкретной реализации. Псевдонимизация и маскирование не равны автоматически необратимому обезличиванию.
## Открытые вопросы
- Где исполняются модели, какие внешние получатели и условия обработки?
- Для каких сценариев обязательна минимизация и есть ли договор поручения обработки?
- Сколько хранить оригинал, маскированный файл, таблицу соответствий, результаты и аудит?
- Какие классы документов обрабатывать и нужно ли обезличивание по умолчанию?
- Должен ли пользователь видеть предпросмотр перед передачей?
- Удаление и выгрузка документов в кабинете; согласия/основания и разграничение полномочий.
## Тесты
PDF без скрытых текстовых слоёв и метаданных; Excel без скрытых листов/формул/комментариев, стабильность идентификаторов контрагентов, сохранение корректных сумм и счетов; невозможность межарендного доступа; утечки в prompt/log/export; ошибки избыточного скрытия.
## Решение
Пока проектировать интерфейс «Анонимайзер» в карточке пользователя, не утверждать глобальный режим обязательного удаления данных. Выбор политики обработки — после моделирования потоков данных, юридического анализа и тестов качества.


## Решение заказчика от 2026-11-22: защищённый оригинал, рабочая копия и неизменяемые версии
**Утверждено:** исходные документы хранятся исключительно в контролируемой серверной инфраструктуре сервиса; внешним ИИ-поставщикам передаются только копии после проверки и удаления/псевдонимизации чувствительных сведений. Отправка оригинала внешнему ИИ запрещена. Учитывать, что даже очищенные данные могут быть чувствительными и не обязательно юридически обезличенными.

### Реестр и идентификация
При загрузке создать document_id UUID и человекочитаемый номер в рамках tenant, например DOC-2026-000124. Оригинал immutable, сохраняет исходное имя/тип, SHA-256, дату, автора, tenant_id, organization_id, исходный номер акта/договора как отдельный атрибут. Оригинальные номера контрагентов не использовать как ключ.
Для каждой очищенной версии — отдельный UUID и номер DOC-2026-000124-A01, -A02, parent_document_id, SHA-256, sanitization_policy_version, status, actor, created_at; для анализа — самостоятельный immutable artifact UUID / DOC-2026-000124-R01, analysis_model_and_version, parent_anonymized_id. UUID являются системными ключами; человекочитаемые номера лишь UI-представление.
Таблица соответствия токенов (псевдонимы -> реальные реквизиты) хранится отдельно, зашифрованно, с узкими полномочиями на обратное сопоставление; не передавать модели. При этом по выходным суммам и датам может сохраняться риск идентификации.

### Хранилище
Три разделённых домена: originals/ (read-once/write-new, deny update/delete для работников анализа, server-side encryption, object versioning/WORM по политике); anonymized/ (только новый объект на каждую обработку); analysis_results/ (новые артефакты). Mapping vault отдельно от них. Пути — UUID, не ИНН/ФИО. Прямых публичных URL нет. Наличие оригинала в неизменяемом хранилище не отменяет правомерного удаления по сроку хранения: реализовать отдельную уполномоченную процедуру удаления с политикой retention и журналом.
Проверять сохранённый SHA-256 оригинала до сопоставления/восстановления результата и после резервных операций. Атомарная запись объекта и реестровой записи, идемпотентность повторных загрузок, журнал ошибок.

### Связь строк и результатов
Для бухгалтерских таблиц хранятся сопоставления source_file_id + sheet + row + column -> anonymized_file_id + sheet + row + column, позволяющие вернуть результат анализа пользователю с точной ссылкой на исходные реквизиты; mapping недоступен внешнему ИИ. Не вставлять реальные ФИО/ИНН в prompt, URL, имя файла или журналы внешней обработки.
Результат анализа только на основе проверенной копии, не перезаписывает оригинал, копию или предыдущий результат.

### Секреты и изоляция
Отдельный service account с правами только на чтение утверждённых очищенных объектов для AI-gateway; оригиналы недоступны ему сетевыми правилами и на уровне IAM. Рабочие запросы внешним ИИ проходят gateway c policy check: copied_only, scrubbed_and_validated, allowed_provider, tenant_consent_or_legal_basis, audit trace. В случае отказа очистки — запрет отправки.

### Приёмочные проверки
Нельзя сохранить новую версию по исходному object key; номер копии уникален при одновременных запросах; невозможно смешать tenants; дубли по имени не перезаписывают файлы; проверка SHA-256; внешнему AI mock не передаётся оригинал; результат связывается с правильной версией и строкой. Проверка PDF: физическая редактировка текстового слоя/метаданных, а не визуальное закрашивание; XLSX: удаление PII из скрытых листов, формул, comments, relationships и metadata. Флаг "анонимно" не выставлять без успешного контролируемого теста.
